# 0009 — Keep a list's filters as a query inside the hash

Status: accepted (round 5)

In the context of R20, which asks that each section's filters (R19) be kept in the page address, so a filtered list can be shared as a link and the browser's Back button returns to the previous filters, in a static site whose routes have lived in the hash since round 1 (`#/planets`, `#/people/1`, `#/search/<text>`) and that has no server to read anything else,
facing the options of a query inside the hash (`#/planets?climate=arid&q=tat`); extra path segments in the hash (`#/planets/climate/arid/terrain/desert`); a real query string before the hash (`/?climate=arid#/planets`), changed with `history.pushState`; and keeping the filters in `history.state` only, with no change to the visible address,
we decided for a query inside the hash, built and read with `URLSearchParams` by the pure functions `listHash` and `parseListState`: field names from `FILTERS` with the lower-case option values of R19, then the name box as `q`, with "Any" and an empty box left out; `parseRoute` ignores the `?` part, so the round 1 to 4 routes keep working; unknown fields and values are ignored; every dropdown change adds a history entry, while typing in the name box adds one and then replaces it (`historyMode`), like the site-wide search of R16,
and neglected path segments (they would clash with entry ids, `#/planets/1` already means planet 1, and need their own escaping for values holding `/`, such as manufacturers), a query string before the hash (it changes the page's real URL, so `python3 -m http.server` and any static host see it, it splits one page state across two parts of the address, and the hash routing would have to watch `popstate` as well as `hashchange`), and `history.state` alone (Back would work, but the address would not change, so a filtered list could not be shared as a link, which R20 asks for),
to achieve filtered lists that can be copied as a link, opened directly, and stepped back and forward with the browser's buttons, using the same `hashchange` routing as every other view, with the address rules unit tested over every option of the real data,
accepting that addresses get long and show field names such as `starship_class` and encoded values such as `gallofree+yards%2C+inc.`; that the field names and option values are now part of shared links, so renaming a field in `FILTERS` or changing how R19 normalises values would quietly drop that filter from old links (they are ignored, not an error); and that `parseRoute` and `parseListState` each read part of the same hash.
